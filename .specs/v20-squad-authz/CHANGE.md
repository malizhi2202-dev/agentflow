# CHANGE: 小队写操作授权（creator 或平台管理员）

- **Change ID**: v20-squad-authz
- **阶段**: 0-change（2026-10-24）
- **规模**: small（~40 行服务层 + 5 处路由 + 用例）
- **挡位**: 完整链（非 UI → 跳过 2a；其余阶段不省）

## Why（为什么做）

`v20-ui-teams` 的 REVIEW 遗留 #4 实测发现：**小隊的写路由只校验"已登录"**，不校验"能不能改这支队"。

- `POST /api/squads`（建队）：任何登录用户可建 —— 这是设计允许的。
- `POST /api/squads/{ref}/members`（加人）、`DELETE …/members/{kind}/{id}`（移人）、`POST …/archive`（归档）、`POST …/assign`（指派任务）：**同样只有 `_user(request)`** → 任何登录用户都能改**别人的**小队、甚至把别人的队归档。
- 而数据模型自己写着：`squad.created_by` = 「写操作授权：creator 或平台管理员（§2.11「小队不是授权单位」）」——**契约写了，代码没落实**。

这是权限缺口（虽然当前单团队自用影响有限，但它属于"信任边界"类缺陷，不能用"还没人用"解释）。

## What（做什么）

在**服务层**加一条唯一判定 `assert_can_manage_squad(db, squad, user)`：`creator` 或**平台管理员**才能写；其余 403 且文案说明原因。
接入 5 个写端点：加成员 / 移成员 / 归档 / 指派任务 /（建队不需要）。
**读**（列表、详情）保持公开——列表本来就是全员可见的组织信息。

## 影响面

- **后端**：`services/team_service.py`（新增异常 + 判定函数）· `routes/teams_api.py`（5 处调用 + 错误映射）。
- **前端**：**不改**。现有页面已把后端 `detail` 原样显示（`v20-ui-teams` AC-10），403 会自动出现在界面上；按 D5「前端零授权判断」也不该预判。
- **数据**：无 schema / 无迁移（`created_by` 早已存在，波 4 就写了）。
- **架构**：0.4 架构级检测**未命中**——在既有模块内补齐授权，不增减模块、不改公共契约形状、不触容量边界。
- **既有口径**：Team 的「非成员 404 / 成员非 owner-admin 403」**不动**；本次只补 Squad。

## 范围排除（这次不做）

1. 小队**转让 owner**：模型没有 owner 概念（只有 `created_by`），不做转让 → 换人只能平台管理员改。
2. 小队**成员级权限**（谁能加人）：不做，口径就是 creator/admin 两人。
3. 不改 Team 的 404 口径（保持"不泄露存在性"）。
4. 前端不隐藏按钮（前端零授权判断）。

## 验收线（粗粒度）

- creator 可加/移成员、归档、指派；非 creator 的普通成员 → **403 + 明确文案**；平台管理员 → 可写。
- 读接口行为不变（列表/详情对全员可见）。
- 后端全量回归：与基线同红（0 新增红）。

## 风险与未知

| # | 风险 | 处理 |
|---|---|---|
| R1 | 现存小队由旧数据创建，`created_by` 为空 → 谁都改不了（只能管理员） | 如实接受：这是"从严"方向；若线上需要，管理员可改（后续可加 backfill，不在本 change） |
| R2 | 403 vs 404 口径与 Team 不一致 | 有意：Team 列表按成员过滤（隐藏存在性有意义）；Squad 列表全员可见，隐藏无意义 → 用 403 说清 |
| R3 | 前端会看到 403 文案，但按钮仍可点 | 符合 D5；如体验差另立 change 做"我创建的队"筛选（v2） |
