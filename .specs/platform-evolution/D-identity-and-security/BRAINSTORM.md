# ① 头脑风暴

## 问题定义

认证中间件的身份来自**请求头**，且**默认 admin**。可复现证据：

| # | 事实 | 位置 |
|---|---|---|
| 1 | 身份取自 `X-User-Id` 请求头；未传则 `user = get_user("admin")` | `backend/main.py` 认证中间件 |
| 2 | `get_current_user` 在 `request.state.user` 缺失时**回退 admin** | `backend/auth.py:181-186` |
| 3 | 唯一缓解＝来源 IP ∈ {127.0.0.1, localhost, ::1} | `backend/main.py` 认证中间件 |
| 4 | 全仓**无 `X-Forwarded-For` / 可信代理处理**（grep 无命中） | — |
| 5 | 口令＝**无盐 `hashlib.sha256`** | `backend/auth.py:19-21` |
| 6 | 默认口令硬编码 `123456`；存在「缺失 password_hash 即重置为 123456」的分支 | `backend/auth.py:108`、`:126-130` |
| 7 | 前端 **109 处**引用 `X-User-Id` | `grep -rn 'X-User-Id' frontend/src` |

**风险链**：`X-User-Id`（客户端自述）+ localhost 闸门。单机默认部署下闸门有效，
**但一旦前置同机反向代理，`request.client.host` 变为 127.0.0.1，闸门对所有外部请求放行**，
叠加身份自述 → **可提权为任意用户（含 admin）**。这是条件性漏洞，不是已被攻破的现状。

## 发散：可选方案

### 方案 A · 加一个共享密钥头
所有请求必须带 `X-Api-Key`，与 `X-User-Id` 配合。
- 优点：改动极小。
- 缺点：密钥仍是**客户端持有**；无法表达「谁登录了」；无法撤销单个会话；前端 109 处调用点全要改。
- 判断：**否**。治标不治本，且把身份问题变成了密钥分发问题。

### 方案 B · 服务端签发会话令牌（**推荐**）
登录成功后服务端签发令牌，中间件从令牌解析身份。
两种形态可选：
- **B1 · HttpOnly Cookie + CSRF 令牌**：浏览器场景最稳，天然防 XSS 窃取；需处理 CSRF 与跨端口 CORS。
- **B2 · Bearer 令牌（JWT 或 opaque）**：对 CLI/脚本友好，与既有「CLI 与 API 对等」方向一致。
- 判断：**B1 + B2 并存**——浏览器走 Cookie，程序化调用走 Bearer。今天是纯浏览器形态，
  但 S4 议题里的守护进程模型必然需要 Bearer，故**表结构应一次设计到位**。

### 方案 C · 只做部署约束（要求必须置于鉴权代理后）
保持现状，文档强制要求「必须部署在带鉴权的反向代理后」。
- 优点：零代码改动。
- 缺点：把安全责任完全外推；且**当前连「闸门在反代后失效」这个事实都没写明**，
  等于要求用户遵守一条他们不知道的规则。
- 判断：**否**（但可作为方案 B 落地前的过渡，条件是**必须同时写明风险**，即 S2 的 C1 同款处理）。

### 方案 D · 引入外部身份提供方（OIDC）
对接 OIDC/OAuth，交给 IdP。
- 优点：企业级最标准，免自研口令体系。
- 缺点：与「零外部依赖、clone 即跑」冲突——总得先有一个本地账号能进。
- 判断：**作为可选增强**，本地账号体系必须保留为默认。

## 关键设计约束（来自竞品教训）

| 约束 | 来源 | 说明 |
|---|---|---|
| **客户端提交的身份头必须由服务端剔除后重写** | Multica：中间件先 `Del("X-Actor-Source"/"X-Agent-ID"/"X-Task-ID")`，仅可信分支重写 | 否则客户端可伪造动作者身份 |
| **同一不变量在两处独立校验** | Multica MUL-2600：URL workspace == token workspace，早期检查 + 中间件 catch-all，明文「不假设前一处覆盖了所有入口」 | 不依赖单点校验 |
| **越权与「不存在」统一返回 404** | Multica：成员查询失败一律 404「workspace not found」而非 403 | 避免用状态码探测他人资源存在性 |
| **第二条数据通道必须独立重新授权** | Multica `scope_authorizer.go:96-101`：「The realtime layer must not weaken this」 | AgentFlow 有 SSE（`/api/runtime/stream`），同款风险 |
| **审计不可用时不降级放行** | Multica：审计写失败则拒绝返回明文 / 回滚更新 | fail-closed 而非 fail-open |
| **未知动作者来源默认人等价，靠评审纪律兜底** | Multica `RequireHumanActor` 是**显式 denylist + 刻意 fail-open**，并要求「新增机器凭证分支时必须同步分类」 | 这是**有意识的取舍**，不是疏漏——但必须配套纪律 |
| **吊销令牌是纵深防御，状态收敛才是主防线** | Multica：成员移除时同事务归档 agent + 取消任务 + 强制离线 | 只吊销令牌不足 |

## 初步判断

主推**方案 B（B1+B2 并存）**，方案 D 作为可选增强，方案 C 仅作为过渡**且必须同时写明风险**。
口令侧独立成项：换自适应哈希（argon2/bcrypt）、移除硬编码默认口令与「重置为 123456」分支、首次登录强制改密。

**顺序很重要**：先纠正表述与消除 fail-open 回退，再做令牌体系。因为即使令牌体系上线，
只要 `get_current_user` 仍会在缺失身份时回退 admin，就仍有一条 fail-open 后门。
