# ④ GD 议题门（评审团裁决）

## 角色判断

### 🟫 架构师（关注改造面与一致性）
**✅ 同意 C1/C2/C3/C4**，理由：这四项都是「把默认值改对」，不引入新概念。
**⚠️ 对 C2 提出改造顺序要求**：前端 109 处 `X-User-Id` 引用是主要成本，
**必须一次性切换**，不能长期双轨（双轨期间 fail-open 后门仍在，且两套身份来源会漂移）。
**要求 C2 分两步**：先服务端同时接受令牌与 `X-User-Id` 但**记录告警**，前端切换完成后
**移除 `X-User-Id` 支持**，并写明移除日期。
**❌ 反对 C9 与 S1 的 C1 并行推进**：两者都在动权限谓词，同时改会造成回归难以归因。

### 🟦 研发负责人（关注成本与回归风险）
**✅ 同意 C1/C3/C4**（成本低、收益明确），**同意 C7/C8**。
**⚠️ 对 C2 的成本提出量化关注**：109 处调用点 + 登录流程 + 所有 API 测试都需要改。
**主张 C2 之前先落 C1**——因为 C1 是单点改动（`get_current_user` 一处），
能立刻消除 fail-open 后门，为 C2 争取时间。
**反对 C6 被低估**：SSE 通道独立鉴权不是「顺手加一行」，需要独立设计订阅授权模型
（哪些流对谁可见、断线重连如何重新授权）。**要求 C6 单列设计任务**。

### 🔴 安全审计师（关注实际防护）
**✅ 同意全部，且主张 C1 是全场最高优先级**，理由：fail-open 回退 admin 与部署形态无关，
是**确定性的后门**；而 C4 处理的条件性漏洞至少还需要反代这一前提。
**❌ 强烈反对把 C3 只当作「换哈希算法」**：`backend/auth.py:126-130` 的
「缺失 password_hash 即重置为 123456」分支是**独立的提权路径**——
只要能影响 users.json 使某账号丢失该字段，即可用已知口令登录。
**要求 C3 拆为 C3a（换哈希）与 C3b（移除重置分支）并分别验收**。
**补充要求**：C4 必须在**启动日志与界面**打印当前部署模式；仅写在文档里等于没有。
**另提**：C8 应明确「同事务」是硬要求——分事务执行会在窗口期内留下可被利用的在线状态。

## 裁决

| 项 | 裁决 |
|---|---|
| C1 消除 fail-open 回退 | **通过（全场最高优先级）** |
| C2 身份服务端签发 | **通过**，**追加**：必须一次性切换、禁止长期双轨；分两步且写明 `X-User-Id` 移除日期 |
| C3 口令哈希 + 清默认口令 | **通过**，**拆分**为 C3a（换哈希）/ C3b（移除重置分支），分别验收 |
| C4 可信代理处理 | **通过**，**追加**：必须在启动日志与界面打印当前模式 |
| C5 域归属双点校验 + 统一 404 | **通过** |
| C6 SSE 独立鉴权 | **通过**，**追加**：单列设计任务（订阅授权模型 + 重连再授权） |
| C7 审计 fail-closed | **通过** |
| C8 状态收敛是主防线 | **通过**，**追加**：同事务为硬要求，不接受分事务 |
| C9 看/跑双谓词拆分 | **通过**，但**排期不与 S1 的 C1 并行**（架构师要求） |

**记录的分歧**：架构师反对 C9 与 S1-C1 并行；研发负责人未反对但要求 C2 前先落 C1。
两者均被吸收为排期约束，**无平票、无全票反对** → 按 R13.2「多数通过」执行。

## 送人工审核门的理由（R18.1）

属 R18.1 的「**把关**」类：C2 会**改变所有客户端的鉴权方式**（109 处调用点），
且 C4 需要**产品层面确认部署形态**（单机 vs 反代后）。
另需人确认一个取舍：**是否接受「未知身份一律拒绝」带来的可用性变化**——
今天「不带任何头也能以 admin 使用」这一行为会被移除，可能影响既有脚本与本地调试习惯。
