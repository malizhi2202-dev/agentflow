# ④ GD 议题门（评审团裁决）

## 角色判断

### 🟫 架构师（关注单点真相与配置边界）
**✅ 同意 C1/C2/C3**，理由：落点已存在（`/api/admin/workflow` + `workflow.json` + 备份轮转），
这是「接管道」而非「造管道」，是全部建议里投入产出比最高的。
**⚠️ 对 C2 提出一条硬要求**：配置必须**单一权威**。
若 `workflow.json` 成为权威，则 `backend/config.py` **不应再出现**阶段默认值，
否则又会形成「配置文件 + 代码默认值」双份真相——正是 C1 要消除的问题。
**要求 C2 明确**：代码中只保留「**首次生成配置时**使用的默认值」，运行时**一律以配置为准**。
**❌ 反对 C3 与 C2 并行**：前端改为异步读接口会引入首屏加载态与失败态，
若同时后端还在改配置结构，两端问题会互相掩盖。**要求 C3 在 C2 稳定后再做**。

### 🟦 研发负责人（关注成本与回归）
**✅ 同意 C1**，且**主张 C1 立刻做**：这是纯重构、行为不变、消除双份真相，风险最低收益明确。
**⚠️ 对 C2 的成本提出关注**：`_detect_phase` 是**文件存在性驱动**，逻辑与阶段表耦合较深
（`STAGE_FILES` / `ARTIFACTS` / `T1-SUMMARY.md` 等命名规则都在代码里）。
把它抽到配置意味着**配置要能表达「哪些文件属于哪个阶段」**，
而不只是阶段名列表——**要求 C2 的设计先明确配置 schema 能否表达现有全部规则**，
否则抽到一半会发现表达能力不足。
**反对 C3 现在推进**：前端 6 处改动 + 异步加载态，属纯 UI 重构，
**优先级低于 C2/C4/C5**（那三项影响数据正确性）。

### 🔴 安全审计师（关注数据正确性与失败模式）
**✅ 同意 C4/C5，且主张这两项优先级最高**，理由：这两条处理的是**数据正确性**，
而非代码整洁度。阶段推断错误会直接让「进度」失真，而进度是护城河③的全部价值。
**❌ 强烈反对把 C4 当作「加几行校验」**：`workflow.json` 是**用户可编辑的文件**
（`PUT /api/admin/workflow` 开放），若无校验，一个拼写错误会导致
**阶段静默丢失**——而今天 `_load_workflow` 未见校验逻辑，这是**已存在的缺口**。
**要求 C4 明确失败行为**：非法配置必须**拒绝保存**并返回具体字段错误，
而不是「保存成功但运行时行为异常」。
**补充要求 C5**：`_detect_phase` 的未知态**必须有可观测表现**（界面与 API 都体现），
否则「标记为未知」在实现上等于「什么也没做」，用户仍会看到错误的进度数字。

## 送人工审核门的理由（R18.1）

属 R18.1 的「**把关**」类：C2/C3 会**改变产品配置契约**（阶段模型从代码变为用户可编辑配置），
这直接影响「不绑定任何开发流程」这句对外定位的兑现方式。
需人确认一个取舍：**是否允许用户自定义阶段模型**——
- 允许 → 兑现定位，但需承担配置校验、迁移与前端异步化的全部成本；
- 不允许 → 则应在产品文档中**修正定位表述**，不再宣称「不绑定流程」。

**这是本轮 5 个子议题中唯一一个「要么改代码、要么改定位」的议题，必须由人裁定。**
