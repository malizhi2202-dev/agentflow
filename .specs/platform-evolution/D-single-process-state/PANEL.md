# ④ GD 议题门（评审团裁决）

## 角色判断

### 🟫 架构师（关注演进路径与依赖顺序）
**✅ 同意全部，并强调执行顺序是硬约束**，理由：C5 依赖 C4，C4 依赖 C1/C2 把仓库弄干净；
顺序颠倒会让迁移与 CI 的产出无法审查。
**⚠️ 对 C5 提出一条必须写入设计的要求**：租约必须**带宽限期（lease_until）+ 心跳续期 + 副本标识**，
缺任一项都无法区分「副本挂了」与「任务还在跑」。**反对**用「固定超时」代替心跳——
长任务会被误判为失联并被重复调和，而重复调和正是本议题要消除的问题。
**要求 C5 明确写出「租约机制解决的是状态一致性，不是恰好一次执行」**——不要过度承诺。

### 🟦 研发负责人（关注成本与回归风险）
**✅ 同意 C1/C2/C3/C6/C7**（低成本高收益），**同意 C4**。
**⚠️ 对 C5 的回归风险提出前置条件**：三处内存状态被外置后，
**所有依赖它们的既有行为都会改变**（限流窗口、退避节奏、队列顺序）。
**要求 C5 落地前先补测试**：现有 8 个后端测试文件不足以覆盖队列/限流/退避的语义，
须先为这三处建立**行为基线测试**，否则改造后无法判断是否回归。
**反对 C8 现在推进**：容器化会放大一切未修好的问题（构建坏了、迁移无账本），
**必须排在 C1–C5 之后**。

### 🔴 安全审计师（关注可用性与数据安全）
**✅ 同意 C2**，且补充一条**被忽视的风险**：`git rm -r --cached node_modules` 只是停止跟踪，
**历史提交中仍包含这些文件**——若 `node_modules` 曾包含私有包的凭据（如 `.npmrc` 相关产物），
则凭据仍在 git 历史里。**要求 C2 增加一步：审查历史中是否含敏感文件，必要时重写历史或轮换凭据。**
**✅ 同意 C6 且主张它优先级最高**，理由：不写明单副本限制，使用者会按多副本部署，
导致**同一调和动作被执行两次**（重复重启、重复替换 Agent）——这是可用性事故，不是性能问题。
**⚠️ 对 C4 提出**：迁移框架必须支持**失败可观测**（哪条迁移失败、失败在哪一步），
否则 fix-forward 纪律无法执行——「向前修」的前提是知道断在哪里。

## 送人工审核门的理由（R18.1）

属 R18.1 的「**把关**」类，需人确认三个取舍：
1. **是否接受「先写明单副本限制」而非立即解决**（C6 vs C5 的排期）。
2. **C2 是否接受「历史审查 + 可能轮换凭据」**的额外成本——取决于该仓库是否曾推送到公共远端。
3. **是否接受 C5 前先补测试**导致的工期延长（研发负责人的前置条件）。
