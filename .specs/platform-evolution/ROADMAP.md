## 一、总览：5 个子议题的结论收敛为 3 个层次

| 层 | 含义 | 子议题 | 特征 |
|---|---|---|---|
| **地基** | 不修则其余全部无法安全落地 | S4 | 纯工程，成本低，风险低 |
| **正确性与安全** | 不修即缺陷（含确定性与条件性漏洞） | S3、S2(C1) | 部分是「把默认值改对」 |
| **能力补全** | 把已有优势做实、补齐缺失的一层 | S1、S5、S2(C2+) | 需新实体或配置化 |

**关键判断**：本轮的 5 个子议题不是并列的，**S4 是其余四项的前置**。
理由：状态不外置则多副本不可能（S2 的守护进程、S1 的团队级配额都要求多副本）；
构建不修复则任何自动化质量门都建立不起来（也就无法安全地做 S1/S3 的大改造）。

## 六、本轮的方法性结论

1. **「有代码」≠「有效果」**：Multica 的 `done` 门只有提示词契约、服务端零校验；
   AgentFlow 的 `npm run build` 脚本存在但必然失败。两者同构——
   **验证标准必须是可执行的，不是「存在即完成」。**
2. **「为什么」比「是什么」更可移植**：竞品最有价值的产出是注释里的理由
   （如 admin 越权读邮箱的具体路径、WS 层为何必须独立鉴权），
   而非机制本身。
3. **空白结论有保鲜期**：本领域 3–6 个月即需重做调研
   （Google AX 2026-03 才创建、kagent 2026-09 才发 alpha1、Roo Code 已关停、Continue 已被收购）。
4. **必须承认定位更正**：原假设「K8s 式 Agent 管控无人做过」**已被推翻**——
   kagent（CNCF）、Google AX、agent-sandbox 都已在这条路上。
   差异化应建立在它们**共同的空白**上（动作级审计、任务队列+防饿死、知识产物监控、零依赖可跑）。

## 第 3 轮新增过审结论（2026-09-22 · S6 + S7 · 用户原话「都通过」）

### 定位级（进文档 §1/§1.6 已执行）
1. **六件套 = 品类入场券**（任务+负责人 / 收件箱+审批门 / 可回放时间线 / 成本归因 / runtime 注册 / 协议化——头部产品 2026-09 全部齐备，multica 51,081★·月 6 release 居首）；**胜负手在三块零先例空白**：画布↔YAML 双向对账（最强竞品只有只读 Mermaid）/ 产物谱系+晋级门禁（品类无对应物）/ **域=配额+沙箱+RBAC 三合一强制边界（无人组装，提为头名空白）**。
2. **诚实性定位句**：无沙箱可以是明写的产品决定（multica 同型：逻辑域+真边界在执行宿主，且把边界下沉到渲染端 iframe sandbox），但不能是没人说清的默认状态——AgentFlow v3 在"Domain 不是安全边界"事实处落此句。
3. **模板市场库内自证**："流程=可挂载技能"已在竞品环境跑通（本机 multica 实例把 9 阶段流程做成 20 个 kit-* skill 挂 34 agent）——知识产物 + 模板市场不是空想。
