# ④ GD 议题门（评审团裁决）

## 角色判断

### 🟫 架构师（关注演进路径）
**✅ 同意 C3 的委托式抽象**，理由：五条沙箱路线并存且无标准，自研或押注单一技术都是把架构
锁死在一个未收敛的赌注上；委托式抽象是唯一可退可进的形态。
**⚠️ 对 C3 的降级路径提出硬要求**：降级**必须是显式的**。若系统在无沙箱时静默退化为进程内执行，
那么「开发机跑得好好的、生产上以为有隔离」会成为必然事故。
**要求 C3 增加一条**：降级时必须在界面、审计与 API 响应三处同时标记 `isolation: none`。

### 🟦 研发负责人（关注成本与可行性）
**⚠️ 有条件同意**，理由：C3/C4/C5 都是高难度项，本轮若同时推进会拖垮节奏。
**提出排期主张**：C1、C2 应**立刻做**（成本低、消除已知风险）；C3/C4 **排到 S4 之后**——
因为 C3 依赖 `Domain` 承载 `egress_policy` 等新字段，而 `Domain` 今天只有 4 字段，
扩字段属 S4 的迁移框架范围（当前是 `database.py` 里 3 条内联 `ALTER TABLE`，无版本账本）。
**反对 C5 单独立项**：其前置条件全在 S4，独立立项会产生跨议题的空转。

### 🔴 安全审计师（关注真实防护效果）
**✅ 同意 C1，并主张它是最高优先级**，理由：把「逻辑分组」说成「安全边界」会让使用者在
错误的前提下做部署决策——**这是安全文档缺陷，不是文案问题**。
**❌ 反对把 C2 当作「已解决」就收工**：凭据加密（AES-256-GCM）只解决**静态存储**，
不解决「Agent 在运行期可读取到明文」这一实际攻击面。**要求 C2 明确区分静态加密与运行期可达性**，
并以「运行期不可达」为验收标准。
**补充要求**：C4 的默认拒绝必须作用于**所有出网路径**，包括工具调用、知识库抓取与渠道回调；
只覆盖主执行路径等于没做。

## 裁决

| 项 | 裁决 |
|---|---|
| C1 纠正表述 | **通过（最高优先级）**——安全审计师与架构师一致 |
| C2 凭据收敛 | **有条件通过**——验收标准改为**运行期不可达**，而非仅静态加密 |
| C3 委托式隔离抽象 | **通过**（排期在 S4 之后），并**追加**：降级必须三处显式标记 `isolation: none` |
| C4 出口默认拒绝 + 工作负载身份 | **通过**，**追加**：覆盖工具调用 / 知识库抓取 / 渠道回调全部出网路径 |
| C5 守护进程模型 | **通过**，**并入 S4 联合设计**，不单独立项 |

**记录的分歧**：研发负责人主张 C3/C4 排到 S4 之后，安全审计师未反对但强调 C1 不可延后——
二者不冲突（C1 与 C3/C4 是不同项），故**无平票**，按 R13.2「多数通过」执行。

## 送人工审核门的理由（R18.1）

属 R18.1 的「**把关**」类：C3 会**改变部署形态**（引入沙箱运行时），C5 会改变**信任模型**
（Agent 跑在用户机器上意味着「代码不出门」但也意味着平台失去执行环境的可见性）。
两者都不是纯技术选型，需要人确认产品承诺的边界在哪里。
