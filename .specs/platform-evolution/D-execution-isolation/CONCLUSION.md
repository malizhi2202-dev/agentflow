# ③ 结论与建议

## 结论

**AgentFlow 目前不具备任何形式的安全隔离，而「隔离域」这个词会让使用者误以为具备。**
今天 `Domain` 只是逻辑分组（`models/domain.py` 4 字段），Agent 在平台进程内执行——这意味着
**一次提示注入即可触达平台凭据与数据库**。这不只是技术缺口，更是**表述风险**：产品文档里
「隔离域」与「安全边界」被混为一谈。

因此建议分两步：**先纠正表述，再补能力。**

## 建议（按优先级）

### C1 · 立即纠正表述：写明「`Domain` 不是安全边界」 `P0` 难度：低（文档/文案）
- 产品文档与界面必须显式声明：`Domain` 是**逻辑分组与可见性边界**，**不是**进程/网络/凭据隔离边界。
- 借用业界已成惯例的措辞姿态：OpenHands「A separate conversation is not a security boundary」、
  Roomote「do not use Docker sandboxes as a multi-tenant isolation boundary」。
- **为何是 P0**：这是把「已知不安全」包装成「看起来安全」的唯一一步，成本最低、收益最高。

### C2 · 凭据收敛：不进 Agent 可达范围 `P0` 难度：中
现状已有基础（AES-256-GCM 加密服务、密钥脱敏 `sk-***`），但**凭据对 Agent 仍可达**。
建议照搬 Multica 三件套：
1. 跨边界传输类型**刻意不含凭据**；
2. 改为**任务级短令牌**按需拉取（只存 hash）；
3. 密钥**独立存储**，使常规读路径在类型/模块层面够不到。

### C3 · 委托式隔离抽象 `P2` 难度：高
定义 `IsolationProvider`（能力协商式），把执行委托给外部沙箱运行时（容器/microVM/gVisor/Kata）。
- **不押注单一技术**：业界五条路线并存、无事实标准（Firecracker/gVisor/Kata/libkrun/Cloud Hypervisor）。
- 参照 `agent-sandbox` 的「**只编排、不放隔离**」定位，避免自建沙箱这一无底洞。
- **保留降级路径**：无沙箱运行时可用时退化为进程内执行，但**必须在界面显式告警**（不是静默降级）。

### C4 · 出口默认拒绝 + 工作负载身份 `P2` 难度：中高
- `Domain` 承载 `egress_policy`，**默认拒绝**、first-match-wins、规则数设上限。
- 身份从「进程」升级为**工作负载身份**（SPIFFE/SPIRE 思路）。
- 参照 kagent `EgressPolicy` 的语义与限额。

### C5 · 守护进程模型（Agent 跑在用户机器） `P2` 难度：高，**依赖 S4**
价值独特（代码不出门、可复用用户机器已登录的 CLI），但**必须先有状态外置 + 任务租约**（S4 的 C1），
否则长连接下的任务分发与在线状态无法可靠表达。**登记为议题，与 S4 联合设计。**

## 明确不做（本轮）

- **不自建沙箱**（方案 B/C 的自研路径）：成本无底、路线未定，且与「零外部依赖单机可跑」冲突。
- **不承诺容器级隔离等于多租户安全**：业界已明确这只是必要条件而非充分条件。
- **不把隔离能力做成默认强制**：默认单机路径必须保持一条 `uvicorn` 可跑；沙箱是可选增强。
