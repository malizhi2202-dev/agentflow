④ 协作协议（平台维护 · 本队不可编辑 · 与 Agent 提示词分账）

Operating Protocol 摘要（被激活即 LEADER · 硬契约）： ①只协调不动手——leader 不亲自执行成员该干的活； ② 每轮一条委派评论——同一轮写多条=多次触发，禁止； ③ 不写 [@Name](mention://agent/uuid) 链接 = 不委派——纯文本 @ 只是提醒，不产生任何运行；这是平台侧硬契约，写错形态不会报错、只会静默不委派（所以必须用「可粘贴 mention」）； ③′ 多条委派评论会互相触发，也会被合并成一次唤醒，所以每轮只发一条；一条评论 @ 多个不同 Agent = 各建一次运行（多个 mention 解析到同一 Agent 只留一次）——「每轮一条」压的是重复唤醒，不是少派；真要多条线并行，就在同一轮里 @ 出去；④ 建子任务指派 与 @mention 二选一——两件事都做=双触发（子任务跑一次 + mention 再跑一次），平台在 evaluated 审计里把这种重复标 double_trigger 并拒第二次； ⑤ 结论停在 in_review，done 留给人工复核——「需人批」规则加在状态转换层（动作者类型 × 目标状态），不只写进提示词。

briefing 注入机制（拼装顺序固定）

leader 任务被 claim 时，平台把下面三段拼到 leader 指令尾部，作为同一次运行上下文；不覆盖平台基础提示，也不写回 Agent 的「能力 · 指令」字段。

  1. Operating Protocol（平台维护 · 全 squad 同一份 · 版本随平台）
  2. 成员名册（带 skills 标签 + 在线态 + 真形 mention 串 · 实时取，非快照）
  3. 本队 instructions（③ 段那份 · squad 自有 · 可即存）

完整链路：平台只读层（随部署更新 · 不落库）＋ 用户指令层（Agent 详情页指令）为前两段；上面三段一律接在 leader 指令尾部，claim 时合成后一并注入运行时系统提示的 ## Agent Identity 节——与 Agent 指令双层模型同一条缝。

拼装结果只在 run 上下文里，看预览抽屉；Agent 详情页的指令区不显示这三段（分账，避免误当 Agent 自己的提示词去改）。

唤醒与去重（平台侧，不靠 leader 自觉）

本表 = 四入口里「指派 + 提及 + 自动化」三路在协作场景下的合并规则；去重只管「同刻不重复」，不管「该停了」（见末行）· 全景对照 board.html · 四入口矩阵 →

成员 run 完成评论兜底唤醒 leader 续跑（run 结束事件 + 评论事件双投递，任一到达即可）· 队列行记 trigger_comment_id（哪条评论叫醒我）幂等
计划 vs 收据coalesced_comment_ids = 计划并入的评论集，实际投喂列表另存一个数组——才能回答「为什么它只跑了一次」两数组分账
同 HEAD 复审同分支同 commit 已出过结论 → 不重跑，复用上次结论并在时间线标 dedup: HEAD 已评审省一整轮
同 (任务, Agent)活跃任务合并去重：leader 连发两次 mention 同一 Agent 同一任务 = 一条 runcoalesced
自触发角色感知抑制：leader 自己写的委派评论不再叫醒 leader、成员也不回触发自己——但人写的评论照样叫醒 leader（人的追问必须进）。全平台唯一一处自动抑制规则，界面必须明写防死循环
轮次无轮次上限（不硬卡 N 轮），靠「每轮一条 + 去重 + 自触发抑制」三条防失控；异常成本走配额硬限与告警刻意不设限
合并 ≠ 终止合并重复不等于决定终止：平台只保证同一时刻不重复入队（同刻重复合并成一次唤醒）；协作何时结束 = 写进队长与成员指令的配置责任，不是平台责任——所以本页「停笔点 / done 归人」这类收口句必须落在 ③ 协作指令里，界面与告警都不替你判「该结束了」指令配置责任
离线成员runtime_offline：委派暂存不丢，心跳恢复后续投，不静默失败；过期判失败走双条件——runtime 静默超宽限 且 该 run 排队同样久（机器忙≠机器没了），判后才升收件箱不丢

三道闸都在状态转换层，不在提示词里（提示词契约 ≠ 门禁）： ① Triage 门——任务处于待受理时，leader 不被叫醒、mention 不产生 run、自动化命中也不跑；人 accept 后放行，人显式 @ 指名除外（人点名派发放行）。 ② in_review / done 分界——leader 与成员只能推到 in_review；done 的写权限在平台层直接拒绝 Agent 作者，连「leader 声称已验收」的评论文本也不认。 ③ 失败升格收件箱——run 失败自动升 action_required，不做机器自愈、不自动重试；重跑按钮只有人有，且重跑保留原角色（原 leader 仍 leader、原名册仍名册）。内建七态 backlog / todo / in_progress / in_review / blocked / done / cancelled 归四 category，语义沿用看板（§6.20）。

⑦ 沉淀与导出（受审模板 · 声明式 · 不含运行细节）

导出小队配置为受审模板

只导声明式内容：squad 名 + 成员名 + skills + 协作指令。不含 id / runtime / 凭据 / 环境变量 / 时间线；新环境按名导入，成员解析不到 → 整包失败并列出缺失清单（宁可不装，不装半支），不静默建 Agent。

为什么动态协作不生成画布 YAML

动态协作不生成画布 YAML——固定编排请去 画布，两者共享路由 / 权限 / 队列底座。小队的时间线是涌现的（leader 每轮按 skills 决定下一跳），画布是声明的（节点与边先画死）；把涌现结果反导成 YAML 会造出一张「看起来可控、其实每次跑都不一样」的假图。

可预测性画布：每轮同图 · squad：同指令可不同跳互补
共享底座自动路由 · 可调用目标判定 · 队列合并 · 配额 · 审计同一套
互转仅「把某条固定委派链沉淀成工作流」这一方向，手工在画布重画不自动反导

⑧ 危险区

归档协作小队 = 不可恢复。与团队归档（可恢复）不同：squad 无资产可托管，留一个空壳只会让人误以为还能指派。归档后——

  • 存量任务再指派给本队 → 403 squad_archived（含自动化规则触发：目标失效，规则自动转 disabled，不静默删）；
  • 停的是「未来指派」，不停「在跑 run」：leader 与成员的在跑 run 不自动取消——要停走各运行的显式停运行动作（如 r-131 的「停止」）；历史与时间线照旧保留、转只读可查。〔2026-2026-10-23 返修：本条原文误写「归档即取消全部在跑 run」，按 multica 事实改为「归档=停未来指派 · 在跑 run 不连带取消」；与团队归档的差别只剩「不可恢复 + 无资产托管」，不再含「谁取消 run」这一项〕

  • 成员不受任何影响（Agent 归团队、人归用户册，池位本来就是引用）；

接收位要能被平台入队
平台的 is_leader_task 只有 Agent 队列能承接；人没有队列，也没有 claim 动作。
在线态要可判定

成本要有主体

归档会断链
