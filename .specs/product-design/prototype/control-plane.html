双通道坦白句（先说清楚，别让人信错东西）：推送通道（WebSocket）只负责快，数据库才是终态——客户端重连后必须重新查询校准；每条推送通道都配轮询兜底，单次断线不会让排队任务卡死。本页队列 / 探针 / 调和三区同此一条口径：断线期间以刷新后回读到的库值为准，不以推送顺序为准。

排队 run 的过期判定 · 双条件 机器忙 ≠ 机器没了

runtime 静默超过 reconnect 宽限期，且该 run 自己排队同样久 —— 两条同时成立才把排队 run 判失败。只看前一条会把「机器只是忙」误杀成「机器没了」；只看后一条会让刚醒过来的机器背上不该背的历史欠账。

三例（演示）runtime 静默该 run 排队判定
机器只是忙12s < 宽限18m > 宽限继续等 · 不判失败
刚睡着的机器上新派的任务40s40s拿完整宽限重计 · 不继承上一任机器的累计时长
机器真没了4m20s > 宽限4m20s > 宽限两条同成立 → 置失败 · 人可直接重试

宽限期数值与机器侧心跳口径以 运行时页 为准（同一条纪律，不在本页重复铺开机器列表）。本页队列里任何一行都不会因单条件被摘掉。

Runtime 回收与清理（reclaim） 自动 · 属状态回收

机制事实
daemon 重启 → reclaim上次未正常结束的 run 由 daemon 重启时自动回收：记失败原因 runtime_recovery、可直接重试。run 不会「卡在运行中」等人去发现，也不会被静默抹掉。
离线判定心跳 15s；异常退出最迟约 3 分钟转离线，不靠人工巡检
自动清理离线 >7 天 且无任何 Agent 绑定（含已归档 Agent 的绑定）的 runtime 自动清理；只有一条成立则留着

reclaim / 离线判定 / 清理三件都是状态收敛级别的自动动作——不改写历史数据、不动 schema（边界见下方「维护作业」与定位对照句）。

本地目录互斥锁事实
存在哪活在 daemon 内存里——不落盘锁文件，daemon 重启即释放。不会出现「上次崩了留个 lock 文件，之后谁都跑不了」这种死局，也不需要人上机器删文件
代价（写清楚）这把锁的强度=一个进程内：跨机器、跨 daemon 不共享，同目录并发不靠它兜底，靠部署纪律（同一路径交给一台机器的一个 daemon）

维护作业（operator-driven 批量作业） 规划 · 未实现 与上方自动调和并列成文 · 永不自动发生

是什么：由人启动、对全库或大批量数据动手的作业——schema 迁移、历史数据修复、批量回填、全量校验。它和自动调和是并列的两条路：调和管状态收敛（回收 / 过期 / 清理），维护作业管数据改写。本页只有它的界面位与纪律，不执行任何真作业。

纪律事实为什么这样定
入口：独立本机监听口只听 127.0.0.1，地址不可覆盖、不对外发布；无应用层鉴权——挡人靠容器权限（能进容器 = 能跑作业）批量写是最难回滚的动作，不把它接到面向用户的鉴权面上；权限模型简单到「你在不在那台机器里」
默认态：dry-run默认只报告「会碰哪些表 / 哪些行、改完长什么样」，不落任何写让人先读计划，而不是先信代码
转 apply 的前置必须同时给：新幂等键（不复用旧键，重复提交即拒）+ 人工担保旗标（我读完这份计划并担保它）缺任一项直接拒、连事务都不开；两样齐了才允许把这份计划真落写，而重放由幂等键挡住——「按两次得到两种结果」不可能发生
事务与预算每请求一个短事务（不拿长事务锁全库）+ 批次预算与墙钟预算双限，任一触顶即停停得下来比跑得快重要；在线库不能被一次回填按住
暂停语义暂停后不自动 resume——必须人再点与 RSI 总闸、自动化失败率门同一条纪律：止损可以自动，恢复必须有人
退出码0 完成　·　2 未竟（有剩余或校验未过，可续跑）　·　1 技术失败「没跑完」和「跑挂了」必须可区分，脚本与人都能按码分支
完成定义全量校验通过 且 remaining=0 才算完成——跑完 ≠ 完成完成是结论，不是进度条到头
