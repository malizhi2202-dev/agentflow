延迟说明：告警巡检每 30 秒运行一次，因此从事件发生到告警出现最多有 30 秒延迟。这是设计取舍，不是故障。

确认 ≠ 修复：「确认」只把告警标记为已读并清掉导航角标；根因仍需在管控面（探针 / 调和）或运行时监控中处理。

失败原因码表 · execution_failed 展开（multica 全量码表精神）

定位：错误码就是给使用者的处置说明书——每条码必须回答「该做什么」，不是堆栈转储；答不出处置的码不算交付完。需人处置的失败，出口不变：升格收件箱「需决策」（action_required）（去收件箱看这条链 ›），与任务看板「run 失败 → 受阻 · 不自动重试」同一措辞，本表只讲成因与处置，不改出口。

自动重试纪律：自动重试只覆盖环境抖动类——默认最多跑 2 次；工具网络中断重 3 次、最后一次延迟约 5 秒再试。两档例外一律不自动重试：自动化 run_only 模式与排队中的 run——怕与下一次排程重叠。凭据 / 额度 / 配置 / 上下文溢出类不自动重试：原因还在，重试只是再烧一次——修好原因后人工重试（重跑按钮只有人有）。失败落状态：run 失败且任务在 in_progress、无其它活跃 run 且无新重试 → 回 todo（重新出现在待派池，不会默默挂在 in_progress）。

错误码哪侧意思（人话）自动重试该做什么
runtime_offline平台运行节点离线（心跳丢失），run 起不来或被打断不 · 等恢复任务暂存不丢；把 runtime 拉起或换绑（§6.3 管控面心跳四态）；runtime 回来平台自动续跑，回来后仍失败会再报。
queued_expired平台排队等待超过期限，被清出队列不 · 排队中的 run 一律不自动重试看容量：队列水位 / 渐进扩容（§6.3）；急用时人工重新入队——不自动重试是怕与下一次排程重叠。
runtime_recovery平台runtime 重启 / 恢复导致 run 中止（与 offline 配对的事件码）不 · 产物半写要先看回放里核对断在哪步、产物是否可疑；人确认后再重跑，别让机器替人决定半写产物算不算数。
environment_prepare_failed平台工作区 / 依赖 / 镜像准备失败是 · 环境抖动类 ≤2 次先让自动重试跑完；两次仍败 → 查镜像与工具链版本（§6.5 运行时），修好后人工重试。
cancelled平台被人工或上层流程主动取消不 · 取消是决策不是故障不算错误：查审计找取消人；不同意取消再人工重跑（取消不计成功率）。
timeout平台运行总时长超预算是 · 环境抖动类 ≤2 次两次仍超时就不是抖动：拆小任务粒度，或调时长上限（边配置与域软限两处，先定改哪处）。
iteration_limit平台步数（迭代）达上限——Agent 疑似原地打转不 · 重跑只会再烧一遍看回放找循环点：任务太大就拆，编排 / 提示词死循环就修，然后人工重试。
agent_blocked平台Agent 挂起：待审批 / 缺授权 / 缺凭据不 · 卡点在解锁去审批中心批掉挂起单或补授权；解锁后沿用同一 run 续跑（挂起 → 同任务延续）。此类对订阅者 / 被 @ 者无条件投递，不会漏。
api_invalid_request平台模型 / 上游网关请求被拒（配置类）不 · 配置类核对模型绑定与参数版本（§6.4 Agent 详情 · 能力）；请求不合法不会因重试变合法——修配置后人工重试。
context_overflow平台输入超模型上下文窗口不 · 上下文类分批输入 / 开摘要压缩 / 换长上下文模型，再人工重跑——原文重放只会再溢一次。
agent_error.network工具工具调用网络中断是 · 重 3 次，最后一次延迟约 5s多半第三次就自愈；三次全断 → 查工具宿主到目标服务的出口（代理 / DNS / 白名单）。
agent_error.timeout工具工具自身超时是 · ≤2 次（抖动档）稳定慢不是抖动：找工具的慢查询 / 外部服务 SLA，必要时改异步回调模式。
agent_error.auth工具工具凭据失效（401 / 403）不 · 凭据类换凭据并重连验证（§6.9 知识库 Notion 401 同一条链：换好令牌再重跑，失败通知随任务推进自愈归档）。
agent_error.rate_limited工具目标服务限流（429）不 · 额度类等配额窗口重置后人工重试；长期受限 → 申请提额或降调用频率。
agent_error.invalid_args工具工具入参不合 schema不 · 配置类修参数模板或工具版本（§6.7 工具库）；Agent 侧多半是描述含糊，补工具说明再重跑。

口径：平台侧码为全量枚举（对齐 multica 失败原因清单）；agent_error.* 是命名空间，样例列 5 条——新工具错误必须带「该做什么」登记进本表才能使用。本表为规划口径：重试次数是执行参数，落地在运行时（§6.10），非当前后端行为。

演示数据说明：三类告警名称与判定函数一一对应（_check_token_exceeded / _check_agent_dead / _check_execution_failed）。第 4 行演示「已被调和自愈」的告警，级别降为 info。「失败原因码表」区块（2026-10-23 补）取 multica 全量码表精神：平台侧 10 码全列、工具侧 agent_error.* 样例 5 条，每码的「该做什么」为规划口径；重试纪律（环境抖动 ≤2 次 · 工具网络中断 3 次且最后一次延迟约 5s · run_only 与排队中不自动重试 · 凭据/额度/配置/上下文溢出不自动重试）与「失败落状态 → 回 todo」是执行语义设计，非当前后端行为。

静默该告警 24 小时？

静默只压通知与角标：规则仍在跑，事件仍进环形缓冲，只是不再打扰。这不是修复，24h 后若仍触发会重新出现在列表。

影响项静默后
导航角标 / 未确认数不计入（3→2）
通知分层（§6.0 ⑫）24h 内不再 ping 负责人
同签名重复告警仍记录「最近发生」，不新增行
根因（工具禁用 / 探针失败）不变 · 仍存在
到期后自动恢复可见，未确认状态回置
