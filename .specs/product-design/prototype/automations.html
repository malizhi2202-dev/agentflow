全局横切本页 = 自动化中心：一张表看完全平台的自动化（负责人可以是任意 Agent 或任意 Squad）。小队详情页 ⑥ 段是同一批规则的局部视图（目标固定为本队），两页措辞与口径逐字一致：动作两档 create_issue / run_only、并发三态 skip / queue / replace、spec_version 版本快照、失败率门「止损非自愈 · 恢复必须人点」。局部视图建规则不改目标；本页新建时负责人二轨自选。

一条自动化 = Runbook（目标 / 背景 / 约束 / 步骤）＋ 负责人（Agent 或 Squad 二轨）＋ N 个触发器。三件事分账：Runbook 说清「要干什么、边界在哪」，负责人决定「谁去干、成本记在谁头上」，触发器决定「什么时候被叫醒」。Runbook 每次运行读当前值（multica 基线口径）——改了立刻生效、不回溯在途 run；agentflow 自证条款 我们额外记 spec_version 快照，见 §H 对照表。

触发器只有 schedule 与 webhook 两类；「手动 Run now」是第三入口、不算触发器。Run now 走同一份 Runbook、同一个负责人、同一种执行模式，只是由人点；它不进「触发器摘要」列、不计触发器数。agentflow 自扩展 · 明写 本页仍保留 v14 的 api 型作第三类触发器——multica 的 API 路径就是 webhook URL / CLI，没有独立的 api 触发型；对照注见 §H 与「＋ 新建自动化」里的 kind 行。

能管自动化 ≠ 能跑它的 Agent。一条规则每次触发，派生执行照旧按链顶人类过「可调用目标」判定（Agent Access 另行判定，规则不授予调用权），也不绕过 triage 受理门与配额硬限——规则不是后门。建与管：任何成员可建；创建者 + 所属 owner / admin 可编辑；协作者可管理但不可转授权（§G）。

并发语义三态唯一化（与小队页逐字同）：skip=在途则跳过本次（不新建）· queue=排队等前一条终态 · replace=取消在途再入队（取消的 run 不计成功率分母）。动作只有两档：create_issue（留痕在任务上）与 run_only（本次不生成任务，只留运行账——界面明写，不谎报）。每次运行记规则版本快照 spec_version——「当时按哪份规则跑的」可回放可归因。失败率门自动暂停是止损，不是自愈：恢复必须人点。自动派生执行同受 triage 受理门约束。

② 一条自动化的三段构成 —— Runbook 归 Runbook，负责人归负责人，触发器归触发器

Runbook（四段 · 必填）

目标要达成什么，一句话可判成败
背景为什么现在做、上下文在哪（任务 / 仓库 / 文档指针）
约束不许碰什么：禁写产物、禁合并、结论停在 in_review
步骤有序动作清单，负责人可偏离但须在结论里说明

每次运行读当前值（multica 基线）：改 Runbook 立即对此后触发生效，不回溯在途 run。版本账本是我们加的，见 §H。

负责人（二轨 · 单选）

Agent直接给该 Agent 入队；成本与配额落它归属的团队
Squad= 给 leader 入队一条 leader 任务（is_leader_task），无成员抢单；成本沿 leader 归因链落 leader 所属团队
不可混指一条规则只认一个负责人；要两条线跑就建两条规则，各自有版本与账
拒因目标已归档 / 当前调用者不可调用 → 403 not_callable · assignee_archived，原样给出，不降级成「保存成功」

归档目标不会连带删掉规则：规则转 disabled，「不静默删」与小队页同一句。详见 小队详情 · 危险区。

触发器（N 个 · 可并存）

schedule可多条并存（工作日 08:30 + 周五 16:00 复盘各一条），互不覆盖；5 段 cron（无秒位）+ IANA 时区
webhook一条规则一个 URL（含遮蔽 token）；载荷 JSON ≤256KiB；事件过滤 + 投递记录
api 自扩展v14 保留的第三类（POST /squads/1/assign · PAT 计 owner）。multica 只有两类的对照注在 §H
Run now第三入口，不算触发器：人点一下，走同一 Runbook / 负责人 / 执行模式，不进触发器摘要列、不计触发器数

单个触发器可独立启停（自扩展 multica 侧仅 CLI，属已知缺口）；整条规则的启停是另一件事——见 §F。

③ schedule 触发器 —— 多 schedule 并存 · 5 段无秒位 · IANA 时区 · Next runs 必显

表达式与时区

段数5 段 分 时 日 月 周 · 没有秒位——最小粒度 1 分钟；要秒级请走代码，界面不提供
解析服务端解析，非法表达式 422 直给错因（不静默按「永不触发」存下来）
时区IANA 名称（Asia/Shanghai · America/New_York · Europe/Berlin），DST 跳变按 IANA 规则；默认 Asia/Shanghai，非默认显式标注（与小队页同句）
并存同一条规则可挂多条 schedule：各自一行、各自可停用，删一条不影响其余
启停agentflow 自扩展 触发器行给「开 / 关」开关；multica 侧只有整条规则启停 + 单触发器仅 CLI，我们把它搬进 UI（已知缺口的补位）

Next runs 预览（必显 · 保存前必须看到）

不预览就不给保存——「我以为每天跑，其实一条都不会触发」是 cron 最贵的错法，界面直接堵掉。

④ webhook 触发器 —— 载荷上限 · 幂等 · 遮蔽与 Rotate · 事件过滤 · 六步推断 · 响应语义

收：怎么把一次投递判成一次可跑的事

载荷JSON ≤ 256KiB，超限 413 并在投递记录留失败原因（不截断后照跑）
幂等Idempotency-Key 命中已见键 → 200 duplicate，只留投递记录、不新建运行；GitHub 另按 X-GitHub-Delivery 去重（两个键分开记账）
凭据URL 内 token 遮蔽显示（af_wh_9f4c…e21）· 写-only 不回显、改密 = 断开重连（同 §6.4 密钥原则）· Rotate URL → 旧 URL 立即失效
签名HMAC 不符 → 401，与业务失败分开显示（一个是门、一个是活；与小队页同一句）
事件过滤一行 = event + 可选 actions；任一行匹配即跑；空规则 = 全收（不是全拒）

六步事件推断（按序取第一个命中的）

  1. 载荷里的 event 字段（显式，最优先）
  2. X-GitHub-Event ＋ 正文 action
  3. X-Gitlab-Event
  4. X-Event-Type
  5. 正文里的 type / action
  6. 兜底：webhook.received（什么都没认出来，仍收、仍记账）

端点与凭据的轮换面在 对外集成面（与小队页「端点与凭据」同一落点）。

响应语义：业务性「不跑」也回 200

200 accepted收下了并派生成运行——运行结果另在运行史里，不在此刻的响应里
200 skipped规则在跑但这次不跑：并发 skip 命中在途、负责人离线（run_only）、门未放行
200 ignored事件过滤未命中，看完就放下
200 duplicate幂等键命中，已有那次在账上

为什么四类都是 200：业务性不跑返 200，防上游重试风暴——上游只对非 2xx 重试，把「过滤掉了」回成 4xx 会让 CI 反复重投。非 200 一族（400 / 401 / 404 / 413 / 429 / 500）留给调用方自己能修的技术性拒绝，明细见抽屉「响应码表」小卡。

⑤ 执行模式：create_issue ⟂ run_only —— 取舍句写在选择器上，不藏在文档里

维度create_issue 建任务run_only 只运行
一句话取舍需要人看或跟人干的活——讨论、状态、运行全部挂在任务上，看板与收件箱都能看到只要结果、不留协作记录的活——只进自动化运行史，没有任务卡、没有评论线
留痕任务（含 AF-xxx）+ run + 订阅者通知 + 审计run + 运行史一行 + 审计；本次不生成任务（界面明写，不谎报）
触发时负责人离线任务照建，runtime_offline 暂存不丢，心跳恢复自动续投（人派的活不能凭空消失）直接 skipped · 不留等待任务——定时器派的活没人补跑，等下去只会攒一库僵尸卡
没有结果时任务还在（可复盘、可人接手）什么都不留：没产出就没有载体，只有运行史里一行终态
订阅者字段有：建单后通知谁（人 / 收件箱 / 委派型订阅者）无（灰显）：不留任务 = 无处通知；要人知道就改 create_issue
成功率口径分母 = 完结（完成 + 失败），replace 取消的 run 不计；两档同口径同上（口径 ▾）
对照落点任务看板 · 收件箱本页运行史（抽屉 · 投递记录旁）· 执行回放

⑥ 两级账本 + Replay —— 运行史是「跑了什么」，投递记录是「外面投了什么」

第一级 · 自动化运行史

每条触发一行（含 skipped / duplicate 造成的「不跑」）：触发源（哪个触发器 / Run now）· 时间 · 状态 · 关联任务或 run · 失败原因。失败原因区分「门」与「活」：401 签名不符与 exit 1 业务失败不同码、不同色。

第二级 · webhook 投递记录

每个到达一行，跑没跑都记：d-xx 投递号 · 解析后事件（六步推断的结果）· 响应（200 四类 / 非 200）· 去重信息（命中哪个键）· 失败原因。

Replay（重放一条投递）

  • 永远新增，不改旧：重放 d-88 生成 d-90，d-88 原样留在账上
  • 不参与去重：幂等键照抄也不判 duplicate，重放就是「我知道我在重复」
  • 签名失败（401）或仍在排队中的投递不可重放——按钮灰显并给出原因

⑦ 失败治理：熔断 · 手动暂停 · 归档 —— 三件事三种后果，界面各写一句

触发方式条件（演示口径）停了什么怎么恢复
失败率熔断（自动）近 7 天 ≥50 次完结且失败率 ≥90% → 自动暂停并通知创建者（收件箱 action_required 同签名合并为 1 条）整条规则：schedule + webhook + Run now 全停修复后人工恢复——止损非自愈，界面不放「自动重试恢复」
手动暂停（人）人点「暂停」；或负责人离线太久、人在收线箱升级后主动停同上三件事一起停（含 Run now，别留一个能跑的口子）；在途 run 跑完为止、不撤回人点恢复，立即重新接三个入口
删除 = 归档人点「归档」（破坏性动作，二次确认模态 + 原因随快照保留）停未来全部触发；历史保留（运行史与投递记录只读可查，可按 af-auto-4 在审计过滤）没有「恢复触发」：要再跑得新建一条规则（新 id、新 v1 快照）
目标失效（附带）负责人（Squad / Agent）被归档规则自动转 disabled，不静默删行（与小队页逐字同）改指一个有效负责人后再启用

⑧ 权限 —— 「谁能管这条」与「这条能不能真跑」是两本账

建 / 改 / 管

新建任何成员可建（不是管理员专属；建完自己就是创建者）
编辑 / 启停 / 归档 / Rotate / Replay创建者 + 所属团队 owner / admin
协作者可管理（改与停），但不可转授权——「加一个协作者」这一步只有创建者与 owner / admin 能做
Viewer运行史与投递记录只读；「详情」抽屉可看，任何写按钮不渲染

能管自动化 ≠ 能跑它的 Agent。编辑权决定你能不能改这条规则；能不能真跑由每次触发时按链顶人类重过的 Agent Access（可调用目标判定）说了算。所以：把规则改对了仍然 403 not_callable 是合法结果，界面必须把这两种「不行」分开显示，并排给出拒因（permission_denied_editor ⟂ not_callable）。同理，自动化不是后门：triage 受理门、配额硬限、人批门（审批中心）一律照过。

⑨ multica 文档基线 ⟂ agentflow 自扩展 —— 借来的口径与自己的加件分行写，不混为一谈

条款multica 文档基线本页做法定性
触发器类型只有 schedule 与 webhook 两类；API 路径 = webhook URL / CLI，不单列两类为基线，另保留 v14 的 api 型作第三类（POST /squads/1/assign · PAT 计 owner）agentflow 自扩展 明写「multica 只有两类」，不假装是对方口径
单触发器启停整条规则可启停；单个触发器启停只有 CLI（已知缺口）触发器行直接给「开 / 关」开关，列表与抽屉各一处agentflow 自扩展
spec_version 版本账本无版本账本；Runbook 每次运行读当前值，改完即生效照读当前值，同时每次运行记规则版本快照agentflow 自证条款 快照是为回归熔断可指回触发时规则（§6.0 ⑨ 留痕「表 + 界面」两步齐）；multica 无此物，别当成基线

响应码表 —— 200 四类都是「不重投」，非 200 都是「你自己改」

响应一句人话
200 accepted收到了，已经派生成一次运行——结果不在这一刻，去运行史看
200 skipped规则活着，这次不跑：并发命中在途、负责人离线（run_only）、门未放行
200 ignored看完决定不管：事件过滤未命中，一行投递记录到此为止
200 duplicate同一件事你已经投过了（幂等键命中），跑的那次在账上
非 200一句人话
400载荷不是合法 JSON / 缺必填字段——上游自己修，别重投同一份
401签名或 token 不符（含 Rotate 后旧 URL）：与业务失败分开显示
404端点不存在或规则已归档；越权探测与不存在统一 404（不用状态码探别人的规则）
413JSON 超 256KiB，原样拒，不截断后照跑
429该端点被限流（护栏在管控面）：按 Retry-After 退避，别硬怼
500我们这边炸了：投递记录留失败原因，上游可以重投

为什么把业务性不跑都回 200：防上游重试风暴。上游只对非 2xx 重试——把「过滤掉了」回成 4xx，CI 会没完没了地重投同一件事。

「近 7d 失败率」列的口径（与熔断线同一把尺）

分母完结 = 完成 + 失败
不计入replace 取消的 run 不计分母（取消是策略，不是失败）· 在途不算完结
skipped不算失败：没结果就什么都不留，只占「触发次数」不占失败数
401 / 413属门不属活：记在投递记录里，不进运行失败率（否则一个 CI 配错签名会把规则刷成熔断）
熔断线近 7 天 ≥50 次完结 且 失败率 ≥90% → 自动暂停并通知创建者（止损非自愈）
与小队页对齐小队页 ⑥ 那行写「7d 内 ≥50 次运行且失败率 ≥90%」——同一把尺：那里的「运行」= 此处的「完结」（取消与在途都不计），两页以本表口径为准
