1产品全景

本章回答：AgentFlow 是什么、给谁用、能干什么、以及明确不做什么。

1.1 一句话定位

AgentFlow 是把 Kubernetes 的管控范式搬到 Agent 世界里的通用编排与管控平台——它不生产 Agent，也不绑定任何一种开发流程；它负责让一群 Agent 可隔离、可路由、可伸缩、可自愈、可观测、可审计。

K8s 管 Pod
Namespace 隔离Deployment 副本Service 路由HPA 伸缩etcd 状态
AgentFlow 管 Agent
隔离域能力分组自动路由渐进扩容记忆系统

1.4 这个产品不做什么

边界即需求。以下为明确排除项，任何后续变更若触碰这些线，需先改本章。

不做原因替代路径
不做 Agent 本身平台是管控面，不是模型/提示词工厂Agent 由用户自带（7 种 Provider × 4 个运行时适配器）
不绑定任何开发流程通用平台，流程是用户的数据而非产品的代码阶段与门禁以项目内配置 + .specs/ 产物表达
不做多集群联邦当前为单控制面；联邦属远景见 §9 Q5 的演进路径
不做「隐式」语义路由默认仍是标签匹配 + 最小连接数的确定性直通；决策小模型层必须域内两步显式启用（登记≠绑定），不配置就零介入——这是用户原话定的铁律change small-model-decisions 已立项、需求门已过（2026-09-22），代码未落地；见 §6.23 §6.24 与 §9 Q20
不引入 Redis / etcd / 消息队列作为必需依赖「零外部依赖」是核心卖点，SQLite 等价承担状态一致性Redis 为可选加速项；无则自动跳过
不做多租户计费与配额结算当前是内部平台形态用量数据已采集（§6.12），结算未实现（待确认）
不做公网暴露面向 localhost / 内网，Host 头白名单校验如需外网，前置反向代理并自行加固（注意：见 §1.5 的安全边界警告）

1.5 竞品坐标：同类产品在做什么，我们站在哪

2026 年 9 月对 67 个开源仓库做了一手调研（证据见 .specs/COMPETITIVE-RESEARCH-2026-09-agent-harness.md）。结论先说：AgentFlow 原先「K8s 式 Agent 管控无人做过」的假设已被推翻——2026 年出现了多个明确以「declarative + K8s 语义 + agent」为卖点的项目。因此本章的目的不是宣称首创，而是说清我们在哪一格、凭什么被选择。2026-09-22 第 3 轮复核的定盘判断：「工作项+负责人 / 收件箱+审批门 / 可回放执行时间线 / 成本归因 / runtime 注册 / 协议对齐」六件套已成品类入场券（当日实抓 20+ 项目，头部产品全部齐备，multica 51,081★ 且 9 月连发 6 个版本）——p19–p22 只是补票。胜负手在三块零先例空白：画布↔YAML 双向对账、产物谱系+晋级门禁、域=配额+沙箱+RBAC 三合一强制边界。另注：品类内已出现「流程=可挂载技能」的实装（multica 本机实例把整套阶段流程做成 20 个 skill 挂给 34 个 agent），佐证 §3 模板市场不是空想。

我们真正的护城河（四条，均已被竞品空白确认）：

① 动作级 RBAC 审计 + 审批闭环——这正是 Endor Labs《The agent control plane needs a security layer》(2026-04) 指出的行业最难项，也是 kagent 的明确短板（其 OSS 版 authorizer 放行所有检查，且审计只到 prompt/reply 日志）。
② 任务队列 + 标签路由 + 最小连接数 + 防饿死——kagent / Google AX / agent-sandbox 全部没有；它们要么靠 A2A 点对点委派，要么由 CRD 直接创建实例。这是 Kueue / Volcano 的地盘，但没人把它接到 Agent 上。
③ 工作流知识产物监控——67 个仓库里无一涉及。这是唯一的品类独占。
④ 零外部依赖单进程可跑——竞品几乎全部要求 K8s + PostgreSQL。clone 下来一条 uvicorn 就能验证，是巨大的采用摩擦优势。

必须承认的差距（同样有据）：

① 没有沙箱——Agent 在平台进程内执行，竞品普遍 gVisor/microVM。这是安全与多租户的硬伤。
② 没有声明式 API 面——有 YAML apply，但没有 CRD 那样的稳定契约与 watch 语义。
③ 没有可观测标准——自建 SQLite 指标，无 OTel/Prometheus，无法接入既有可观测栈。
④ 没有 A2A——协议层已收敛（A2A v1.0.1 赢家通吃，ACP 已归档），缺席意味着无法被别人的 Agent 调用。
⑤ 没有协作层——无工作项、负责人、收件箱；Multica 的整个产品都建在这一层上。

1.5.3 三条安全边界警告（改文档不改代码，但必须写明）

风险事实依据后果
身份是客户端自述的认证中间件从 X-User-Id 请求头取身份，未传则默认 admin（backend/main.py 认证中间件）任何能发请求的进程都可冒充任意用户
localhost 闸门在反代后失效唯一的缓解是「来源 IP 必须是 127.0.0.1」，且无 X-Forwarded-For / 可信代理处理一旦前置同机反向代理，闸门对所有外部请求放行，叠加身份自述 → 可提权为 admin
口令与默认值口令为无盐 SHA-256；默认口令硬编码 123456，且存在「缺失 password_hash 就重置为 123456」的自愈分支弱口令 + 快速哈希，离线爆破成本极低

上表只陈述代码事实与部署条件，不代表当前默认部署（localhost 单机）已被攻破。列在此处是因为「不做公网暴露」这条边界（§1.4）一旦被绕过，代价是 admin 权限。

2核心概念

本章回答：AgentFlow 用哪些名词思考问题，这些名词之间是什么关系。概念定名后，§3 架构与 §5 指南才可指认。

概念地图：隔离域 ⊃ 能力分组 ⊃ Agent；Agent 由 编排拓扑 连成链路；编排的期望状态由 Reconcile 调和；Agent 的存活由 探针 判定；Agent 的产出沉淀为 工作流知识产物 与 记忆/知识库；一切变更经 权限 判定并落入 审计。

2.1 隔离域 Domain

一句话定义

Agent 的命名空间：一组 Agent 的可见性与归属边界，对应 K8s 的 Namespace。

为什么重要

没有域，开发/测试/生产的 Agent 会混在同一个扁平列表里——这是现有编排类产品的共同盲区。

关键规则

  • 域的归属字段是 agents.domain_id，可为 NULL；NULL 一律视为属于默认域。
  • 系统启动时自动创建默认域（name='默认域', owner_id='admin'）。
  • 删除域不删 Agent：外键为 ON DELETE SET NULL，域内 Agent 回归默认域。
  • 域归属于创建者；admin 可管理所有域。

与其他概念：域是能力分组的容器；路由与扩容都以域为作用范围；项目可见性（project_ids）与域是两套独立的可见性维度。

2.2 能力分组 Capability Group

一句话定义

域内部的中间层：按 Agent 的 capabilities 自动派生的分组，把「域 → Agent 列表」变成「域 → 能力组 → Agent」。

为什么重要

一个域里 20 个 Agent 平铺不可读；按能力聚合后，一眼能看出「code-review 这组 3 个里挂了 1 个」。

关键规则

  • 虚拟分组，零新增表：分组完全从 agents.model_config_json.capabilities 派生。
  • 多层归属：一个 Agent 有多个 capability（如 ["code-review","python"]）时会同时出现在多个组里——这是有意为之，不是重复渲染。
  • 没有 capabilities 的 Agent 归入「未分类」组。
  • 每组显示健康概要 N healthy / M total；判定口径：running / standby 计为 healthy，其余计为 unhealthy。

与其他概念：能力分组是展示层派生，不是权限边界——它不改变可见性，只改变组织方式。真正的过滤能力由 GET /api/agents?capability= 提供。

平台的价值不在「跑一个 Agent」，而在「同时管住一群 Agent」——所以 Agent 必须是一等实体，而非流程里的一个步骤。

2.5 Reconcile 调和

一句话定义

控制循环：持续比较期望状态与实际状态，发现漂移就自动收敛。

为什么重要

「部署完就祈祷」是同类产品的通病；调和循环把「Agent 挂了要人发现」变成「系统自己发现并修」。

修复级别色标判定条件（_classify_action）语义与动作
safe 绿unhealthy == 0 且 drift_count == 0无需操作——状态正常，本轮不动作
caution 橙异常数 ≥ 1，且未达 dangerous 阈值少量异常，可自动修复——如自动重启、等待在途任务收敛
dangerous 红异常数 > expected/2，或异常数 ≥ 3严重异常，需人工介入——如终止并替换实例；不自动执行

拓扑感知：修复前会检查拓扑依赖（_topology_safe_pause），避免修一个节点把整条链路卡死。退避：_should_backoff 按 [1,2,4,8] 秒递增退避，连续失败 3 次后暂停该实例的本轮调和。审计：每次调和动作经 _write_audit 落盘。

2.6 探针与健康

一句话定义

周期性探活：对每个 Agent 解析出健康端点、发探测、记录结果与时间线。

为什么重要

健康是调和、路由、扩容、告警四个模块的共同输入；没有可信的健康信号，其余全是盲调。

  • 健康端点解析：优先 base_url + /health，回退到显式 health_url；两者都没有则判定为不可探活（返回 None）。
  • 凭据脱敏：探针输出与日志中的 API Key 一律脱敏为 sk-***（覆盖 sk- 与 sk-ant- 两种前缀）。
  • 时间线：每次探测的通过/失败进入 Agent 详情的探针时间线（§6.4）。
  • 限流：管控面 /probes 端点带滑动窗口限流；当前限流器为进程内内存实现，多进程部署时各自计数（已知限制）。

2.8 记忆与知识库

一句话定义

知识库是外部资料的摄入管道（文件 → 分块 → 嵌入 → 可检索）；记忆是Agent 可读写的上下文存储，可跨 Agent 共享。

为什么重要

「新 Agent 代替旧 Agent 时上下文全丢」是常见痛点；域级共享记忆让接替者能继承前序结论。

知识摄入管线

上传→ 类型白名单校验→ 大小校验（≤10MB）→ 文件名净化→ 落盘 uploads/{agent_id}/→ 分块 chunk→ embedding→ indexed
  • 类型白名单：.docx .js .json .md .pdf .py .txt；其余（含无后缀）一律拒绝。
  • 路径穿越防御：上传 ../../../etc/passwd.txt 会被清洗为 passwd.txt，不逃逸目录。
  • 状态流转：uploading → processing → indexed，无需人工干预。
  • chunk 形态：key = {filename}_chunk_{N}，memory_type = "document"，支持语义检索。

2.9 审批与人工闸门

一句话定义

把「机器不确定 / 后果不可逆」的决策点显式暴露给人：流程在此挂起，等人放行。

为什么重要

全自动的 Agent 链路在破坏性动作上不可接受；闸门是「自动化」与「可控」之间的接缝。

  • 两种形态：编排里的 human-approval 连线策略（图上的一个节点），以及独立的审批中心（§6.17，集中处理待办）。
  • 持久化：审批请求落在 human_approvals 表，刷新不丢。
  • 与调和的配合：dangerous 级修复、以及提交/破坏性落盘前的人工关卡，走同一套审批语义。

2.10 角色与权限

一句话定义

两级模型：角色（admin / user）决定基础权限集合，权限点（6 个）决定能做什么，另有项目级可见性决定能看什么。

为什么重要

管控平台的操作不可逆性高（删域、停流程、改用户）；权限必须是显式的白名单而非默认放开。

权限点名称说明危险
project:read查看项目查看项目、变更、文档内容—
project:write编辑项目修改配置、文件、门禁—
project:delete删除项目删除变更 / 产物 / 角色危险
workflow:stop停止流程中断正在执行的流程危险
user:manage用户管理创建、编辑、删除用户及分配权限危险
audit:view查看审计查看审计日志—
  • admin：拥有全部 6 个权限点，且直接放行所有权限检查（豁免）。
  • user：默认零权限，全部由 admin 通过 custom_permissions 显式分配。
  • 项目可见性：admin 未指定 project_ids 时表示「全部可见」；普通用户只能看到被分配的项目；未分配任何项目 = 看不到任何项目。

与其他概念：权限决定 §5.0 的模块可见性，并直接映射到 §7 的角色权限矩阵。

2.7 决策模型（System One）已立项 · 未实现

本节回答：小模型在平台里是什么对象、凭什么敢让它替大模型做决定。

定义：与生成式大模型相对，决策模型不写文本——输入「状态 + 类型化问题 + 选项集（≤26）」，一次前向输出带校准概率的决策，三型：Choice（N 选 1）、Bool（命题为真概率）、Score（有序档位分布及期望值）。范式出处 Jev（TypeSafe AI，2026），社区已有 Qwen3.5-2B Apache-2.0 复刻（本地 Q4 仅 1.3GB，单决策 ~80-110ms，ECE 0.017）。

校准是它敢上岗的执照：「说 80% 就真的 80% 对」意味着概率可直接当置信度用——低于域配阈值（默认 0.6）自动升级大模型（escalated），服务失败即回退直通路由（decision_fallback）。这构成平台的快慢分层：便宜的确定性小决策在前，昂贵的复杂推理在后。

铁律：两步制显式启用——第一步登记进目录（连通、健康态），第二步按用途逐个绑定（路由决策 / 对话分诊 / 简单任务派发，三个独立开关，全默认关）。未绑定 = 决策代码路径零调用，界面无「建议启用」式骚扰（用户原话：不显性指定或没配置就不要用了）。

微调闭环（域内专属）：域 owner 显式开启后，用本域对话与记忆数据（PII 脱敏 + 数据指纹台账 + 可回放「哪些会话被用过」）编排本机 LLaMA-Factory 训练专属决策模型；产物按版本登记血缘（基座+配方+数据指纹），过三指标自测（准确率 / ECE / 与前一生产版本决策一致率，默认门槛 accuracy ≥80% 且 ECE ≤0.05）才允许切生产——门禁在状态转换层（服务端），不是提示词约定（§1.6.5 纪律 ① 的自家应用）。硬件不达标？微调入口灰显并明写缺什么，推理轨不受限。

# agent-domains — 需求文档

> 版本: 1.0
> 状态: draft
> 创建: 2026-07-06

## 概述

为 Agent 控制面板增加 **隔离域（Domain）** 功能，允许用户将
Agent 按域（如：开发域、测试域、生产域）分组管理。

## 功能需求

### FR1: 域 CRUD
- 创建域：name（必填）、owner_id（默认当前用户）
- 删除域：将域内所有 Agent 的 domain_id 置为 NULL（回归默认域）

### FR2: Agent 归属域
- Agent 表新增 `domain_id` 字段（可为 NULL）
- GET /api/agents?domain_id=X 按域过滤

## 验收条件

- [ ] 域 CRUD API 正常工作
- [ ] 删除域后 Agent 回归默认域
- [ ] TypeScript 无新增编译错误

9常见问题

本章从「这个产品不做什么」（§1.4）与用户反问高频点派生。

Q1 · 它和 Dify / LangGraph / CrewAI 这类框架有什么本质区别？

A：那些是构建 Agent 的框架，AgentFlow 是管控一群 Agent 的控制面。类比：LangGraph ≈ 写应用的库；AgentFlow ≈ 跑应用的 K8s。框架关心「怎么把一个 Agent 编出来」，AgentFlow 关心「Agent 上线后如何隔离、路由、扩容、自愈、可观测、可审计」。因此 AgentFlow 不生产 Agent——Agent 由用户自带（7 种 Provider × 4 个运行时适配器）。

Q2 · 为什么不直接依赖 Redis / etcd / 消息队列？

A：因为「零外部依赖」是核心主张（§1.4）。用户 clone 下来 uvicorn main:app 就能跑，不需要先搭基础设施。状态一致性由 SQLite 承担，Redis 存在则用于加速、不存在则自动跳过，不构成启动阻塞。代价是：多进程部署时进程内的限流器与调度状态各自独立（已知限制，见 §2.6）。

Q3 · 删除一个隔离域，里面的 Agent 会一起被删吗？

A：不会。域与 Agent 的外键是 ON DELETE SET NULL：删除域只是把域内 Agent 的 domain_id 置空，它们会回归默认域。这是刻意设计——域是「组织方式」，不是「生命周期容器」。需要真正删除 Agent 必须显式调用 Agent 删除接口。

Q4 · 同一个 Agent 为什么会出现在两个能力组里？是 bug 吗？

A：不是 bug，是多层归属（§2.2）。一个 Agent 的 capabilities 可以是 ["code-review","python"]，它就应该同时出现在 code-review 组和 python 组——因为「按能力找 Agent」时，两个入口都该找到它。能力分组是展示层派生，不新建表、不改变归属。

Q5 · 支持多集群 / 联邦部署吗？

A：不支持，且这是明确的边界（§1.4）。当前是单控制面形态。若要演进，路径是：先把「域」抽象为可跨控制面寻址的逻辑单元，再引入控制面之间的注册与转发协议；这属于远景，未实现（待确认）。

Q6 · Agent 挂了要多久才能被发现和恢复？

A：取决于两条循环：探针周期决定「多久发现」，调和决定「多久恢复」。探针连续失败即判定为漂移；safe 级动作（如自动重启）直接执行，caution 级会先退避等待在途任务收敛，dangerous 级（如终止并替换）会转人工审批而不会自动执行。告警另走 30 秒巡检，因此告警出现最多有 30 秒延迟。

Q7 · 为什么审计日志查不到更早的记录？

A：审计写在与数据库分离的 audit.jsonl 文件里（跨项目共享），超过 1 万行自动轮转归档，只保留最近 5 份（§5.15）。所以更早的历史确实不可查。需要长期留存请定期导出——这是有意的容量取舍，不是 bug。

Q8 · 普通用户登录后什么都看不到，是权限配错了吗？

A：大概率不是。user 角色默认零权限——不勾选任何权限点、不分配任何项目时，导航里只剩「对话中心」。这是刻意的白名单设计（§2.10）：管控平台的操作不可逆性高，所以默认关闭而非默认放开。管理员需在「用户管理」中显式分配权限点与可见项目。

Q9 · 为什么改了 .specs 里的文件，界面上阶段没变？

A：产物扫描有 5 秒 TTL 缓存（§5.18）。保存后稍等再刷新即可。另外，保存前会自动备份到 backup/（保留最近 5 版），需要时可回滚。

Q10 · 编排里配置了 human-approval 边，会不会超时自动放行？

A：不会。人工闸门是阻塞式的：不决策则流程一直挂起（§2.9）。这是安全默认值——自动放行会让闸门失去意义。如果担心流程长期悬挂，应在审批中心配置提醒或在编排里为该边显式配置超时后的异常分支。

Q11 · 知识库能上传多大的文件？支持哪些格式？

A：单文件上限 10MB（正好 10MB 可通过），白名单为 .docx .js .json .md .pdf .py .txt——其余格式（含无后缀文件）一律拒绝。超限返回 400 而非 413。文件名会被净化：上传 ../../../etc/passwd.txt 会存成 passwd.txt，不会逃逸目录（§5.9）。

Q12 · 13 种连线策略是不是过度设计？

A：不是。竞品的连线策略普遍只有 2–4 种，导致复杂链路必须靠「一个节点里塞代码」绕过。AgentFlow 让每条边独立承载重试、超时、Token 上限、安全栅栏、脱敏、IO Schema，这些在真实生产链路里都会用到（§2.4）。如果只用 sequential 就够，也完全可以只用一种——多出来的不是负担，是可选空间。

Q13 · 「K8s 式 Agent 管控」是 AgentFlow 首创吗？

A：不是，这一点必须说清楚。2026 年的调研（§1.5）推翻了「没人做过」的假设：kagent（CNCF Sandbox，v1.0.0-alpha1）已用 kagent.dev/v1alpha3 CRD 存期望配置并做 reconcile；Google AX（4,530★）已提供 ax apply -f / ax watch / ax suspend 与 microVM 隔离；kubernetes-sigs/agent-sandbox 是 SIG Apps 的沙箱编排器。所以 AgentFlow 的定位不是「首创」，而是「在没有 K8s 的前提下提供可验证的管控」——零外部依赖、单进程可跑，这是它们都做不到的。差异化的四条护城河见 §1.5.2。

Q14 · 那 AgentFlow 凭什么被选择？

A：四条，且每一条都已被竞品的空白确认（§1.5.2）：①动作级 RBAC 审计 + 审批闭环——这正是行业公认最难、kagent 明确缺失的（其开源版 authorizer 放行所有检查）；②任务队列 + 标签路由 + 最小连接数 + 防饿死——kagent、Google AX、agent-sandbox 全部没有；③工作流知识产物监控——67 个仓库中无一涉及，是唯一的品类独占；④零外部依赖单进程可跑——竞品几乎都要求 K8s + PostgreSQL。

Q15 · 它最该先修什么？

A：按 §1.6 的排序，P0 全部是「修错」而不是「加功能」。其中三项最紧迫：①构建已经坏了——npm run build 因 32 个 TypeScript 错误必然失败，等于项目没有可用的生产构建；②仓库卫生——node_modules 被 git 跟踪（35,847 个跟踪文件里 35,517 个是它，真实代码只有 273 个）；③身份是客户端自述的——认证中间件从 X-User-Id 请求头取身份且默认 admin，唯一的缓解（localhost 限制）在前置反向代理后会失效。前两项决定别人能否跑起来，第三项决定跑起来后是否安全。

Q16 · 「单进程」这句话在文档里意味着什么？

A：意味着「自动路由 / 渐进扩容 / 自愈」这些能力在多副本下各自为政。原因是三处关键状态都是进程内存：调度队列与标签映射（scheduler_service._queue / _task_labels）、控制面限流（control_plane_api._rate_limit_store）、调和退避（reconcile_loop._backoff_state）。因此当前必须按单副本部署理解。这是 P0-9 要求「先写明」的原因，也是 P1-7（状态外置 + 租约）被列为地基的原因。

Q17 · 为什么不干脆跟着 kagent 做 CRD？

A：因为那会放弃 AgentFlow 唯一不可替代的优势：不需要 K8s 就能跑。kagent 的代价是双层状态（其架构文档明确写 AgentInstance「不是 Kubernetes 资源」，运行时状态在 PostgreSQL），并且要求集群、CRD 安装、PostgreSQL。AgentFlow 的选择是用 YAML + SQLite 表达同一套声明式语义，换取「clone 下来一条 uvicorn 就能验证」。要补的不是 CRD，而是 CRD 背后的条件语义（spec/status/conditions 与 observedGeneration，见 P1-8）。

Q18 · 「IM 原生工作场所」和「对话内嵌团队层」这两条路线怎么算？

A：都是真实路线，但都不是我们的对位。OCTO（1,060★）把 IM 当内核——工作场所即聊天；dsh-agent-teams（1,766★，2026-08 立）把团队层嵌进单个 harness 会话——一条 prompt 变 captain。AgentFlow 是管控面：对话中心是众多入口之一（multica 实测 132/139 运行由评论触发，证明对话入口是主通道之一，值得做深），但隔离域、Reconcile、产物谱系这些不随对话消失的持久对象才是平台本体。三条路线在「工作项+负责人」面上会合，在「期望态与边界」上分道。参照 §1.6.6 的 dsh-agent-teams 行与 §6.0 ④⑩⑫。

Q19 · multica 已经是 51k★ 的六件套全家桶，还追赶什么？

A：正因为六件套成了入场券（§1.6 定盘句），追赶的定义变了：不是抄它的 board，而是守住它没有的三样——画布↔YAML 双向对账（它只有 board，最强同类 AgentTeams 也只到只读 Mermaid）、产物谱系+晋级门禁（品类无对应物，multica 的 issue↔run↔diff 停在审计素材层）、域=配额+沙箱+RBAC 三合一强制边界（它明写无 OS 沙箱、真边界在执行宿主；K8s 阵营有沙箱没工作台）。三样各成一件，「multica + 画布 + 自愈」和「kagent + 工作台」这两个没人完成的组合就是我们的位置。

Q20 · 决策小模型这么香，为什么不默认开着？

A：因为它的价值前提是「校准过的概率能当置信度用」——而复刻模型卡也明写：只在训练过的任务族上校准近乎完美（ECE 0.017），没见过的任务类型只保持基座准确率。默认替所有客户的流量做决定，等于拿一个没验证过的任务分布去赌校准仍然成立，赌输了就是无声的路由劣化。所以产品决定是（用户原话「不显性指定或没配置就不要用」）：提供能力、两步显式启用、未绑定=直通零调用（AC-0 可用审计计数=0 验证）、低置信自动升级、失败必回退——小模型上岗的每一步都有签名，退路永远是那个无聊但可靠的直通路由。另注：微调数据不显式开启就绝不出域，这条没有中间态。
